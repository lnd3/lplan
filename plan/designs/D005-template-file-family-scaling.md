## What

Every `something.md.template` implicitly defines a **file family**: the
instantiated `something.md` is the root, and any number of companion files
(`something_extension.md`, `something_tmp.md`, `something_learnings.md`,
`something_whatever.md`) may exist alongside it. The root stays lean and
template-shaped; depth scales horizontally into companions.

This applies uniformly to every template in lplan — plan root files
(`FOCUS`, `REFLECTION`, `CHANGELOG`, `WORKFLOW`, `AXIOMS`), entity files
(`P001`, `D018`, `A011`), and any repo-specific templates.

## Why

Single files grow unbounded when content doesn't fit the template shape.
Two failure modes observed in practice:

1. **Format corruption**: `REFLECTION.md` accumulated section-header entries
   because one-liners weren't enough for the content — breaking the format
   that tooling and workflow rules rely on.
2. **Truncation**: `MEMORY.md` hit 212 lines and was silently cut by the
   agent context window, losing the Plans section that was the whole point.

The current system has no structural answer for "I need more depth than the
template allows." The result is either bloat (one file does everything, format
drifts) or silence (content is dropped because there's nowhere to put it).

File families give content a home without corrupting the root's format or
blowing the context budget.

Alternatives considered:
- **Longer templates**: just make the template bigger. Rejected — defeats the
  purpose. A longer `REFLECTION.md.template` still produces a single file
  that grows without bound.
- **Subdirectories per entity**: `D018/index.md`, `D018/learnings.md`.
  Rejected — breaks the flat naming convention, complicates `plan generate-index`
  path resolution, and makes `ls plan/designs/` harder to scan.

## How

### Naming convention

Companion files use `{root}_{suffix}.md` (underscore separator):

| Suffix | Semantics | Properties |
|---|---|---|
| `{root}.md` | Template-shaped root; always lean | Bounded by template structure |
| `{root}_extension.md` | Content that doesn't fit the template shape | No format constraint |
| `{root}_tmp.md` | Scratch / working notes | Explicitly ephemeral; deleted when done |
| `{root}_learnings.md` | Scoped append-only learnings for this entity | One-liner format, like REFLECTION |
| `{root}_history.md` | Audit trail / historical record | Append-only; never pruned |

Any suffix is valid — the convention is open-ended. The above are the
canonical ones that tooling knows about.

### Linking

The root file links to companions when content is referenced:

```markdown
## Active

P003 Phase 1 next — see [FOCUS_context.md](FOCUS_context.md) for background.
```

Or inline in entity Log sections:

```markdown
## Log

2026-08-30 — Design phase complete. Extended notes in D005_learnings.md.
```

### Tooling rules

- `plan generate-index`: includes root files (`*.md`); excludes companions
  from the main tables (they are not entities). Companions appear as
  "See also" links in the entity's row if they exist.
- `plan validate`: validates root files against their template schema;
  skips `*_tmp.md` entirely; validates `*_learnings.md` for append-only
  format if the suffix is `_learnings`.
- `plan check-refs`: follows links in root files to companion files;
  flags dead companion links.
- `plan generate-index --include-companions`: optional flag to surface
  companion files in output (for auditing).

### Template changes

Each `something.md.template` gains a trailing comment block:

```markdown
---
*Companion files: `{name}_extension.md` for overflow content,
`{name}_tmp.md` for scratch, `{name}_learnings.md` for scoped
learnings, `{name}_history.md` for audit trail. Any suffix is valid.
Delete companions when content is merged or no longer needed.*
```

This makes the convention discoverable from any template without
requiring agents to remember it from workflow docs.

## Where

**Data ownership:**
- Root `something.md`: template-shaped, bounded, generated by `plan init`.
- Companion files: unstructured (or lightly structured for `_learnings`);
  created ad hoc as content demands; not generated by `plan init`.
- `plan/` directory: companions live beside their root (same directory).
  Entity companions live in the same subdirectory as the entity.

## Constraints

- Root files must remain template-shaped. Adding content to a root that
  should go in a companion is a format violation — same as corrupting REFLECTION.
- Companions are NOT entities. They have no frontmatter, no status, no ID.
  They are auxiliary to the root.
- `_tmp` files are the agent's working scratch. They must be deleted (or
  committed with a note) before the session is closed. They are never
  committed as permanent record.
- Companion files do not appear in `plan/INDEX.md` entity tables.

## Migration

Non-breaking. Existing repos need no changes — companions are opt-in.
The convention becomes active the moment a repo creates its first companion.

Template comment blocks are the only template change — append-only, no
existing content altered.

## Testability

- `plan validate` ignores `*_tmp.md` → no validation errors from scratch files.
- `plan check-refs` follows companion links → dead links caught automatically.
- A repo with an existing `REFLECTION_extension.md` loads correctly in all
  existing tooling (it's just a markdown file; nothing breaks).
